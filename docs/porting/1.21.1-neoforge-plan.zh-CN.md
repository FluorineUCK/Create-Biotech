# Create: Biotech 1.21.1 NeoForge 全量迁移方案

## 目标与完成定义

从当前 `main` 的 Minecraft 1.20.1 Forge/LegacyForge 基线建立两个长期分支：

- `1.20.1`：冻结并维护现有 1.20.1 实现。
- `1.21.1`：承载 Minecraft 1.21.1 + NeoForge 的完整迁移。

`1.21.1` 只有同时满足以下条件才算迁移完成：

1. 模组主源码、悦灵物流子模块、资源、数据生成、发布脚本和本地 Quick Play 基础设施均已迁移。
2. 使用 Java 21 和 NeoForge 1.21.1 工具链可以从干净工作区完成构建。
3. Create、Registrate、Flywheel、Ponder、JEI、Jade 和 MixinExtras 使用 1.21.1 NeoForge 兼容版本。
4. 所有注册项、存档数据、网络包、菜单、实体、方块实体、配方、渲染、Ponder 场景和兼容入口至少完成启动级验证。
5. `quickPlayClient` 能构建并部署模组，启动指定实例，成功进入测试世界；日志中不存在本模组导致的加载失败、Mixin 注入失败、注册错误或数据包错误。

## 已知基线与迁移规模

当前基线为：

- Minecraft `1.20.1`
- Forge `47.1.33`
- Java `17`
- ModDevGradle LegacyForge `2.0.107`
- Create `6.0.8-291`
- Ponder `1.0.91`
- JEI `15.20.0.130`

初步清点结果：

- Java 文件：约 423 个
- 资源文件：约 661 个
- Mixin：约 60 个
- 直接引用 Forge API 的 Java 文件：约 163 个
- 直接引用 Create/Ponder 等 Create 生态 API 的 Java 文件：约 292 个

因此迁移按基础设施、平台 API、Create 生态、资源数据、运行验证分层推进；不以“能编译”代替“能进入世界”。

## 分支与提交策略

1. 从当前干净的 `main` 提交创建 `1.20.1`，不在该分支混入 1.21.1 改动。
2. 从同一基线创建 `1.21.1`，迁移方案和所有移植改动只进入该分支。
3. 每个阶段使用独立、可构建或有明确失败清单的提交；不把大规模自动替换和行为修复混在同一提交。
4. 迁移期间保留资源 ID、注册名和网络语义，避免无必要的存档不兼容。

## `ref/` 管理方案

参照 `D:\Files\ponderer`，将本地参考源码按 Minecraft 版本组织：

```text
ref/
├─ SOURCES.md
├─ 1.20.1/
│  ├─ Create/
│  ├─ Ponder/
│  └─ JustEnoughItems/
├─ 1.21.1/
│  ├─ Create/
│  ├─ Ponder/
│  └─ JustEnoughItems/
└─ _legacy_pre_reorg_<timestamp>/
```

规则：

- 使用浅克隆，目录整体继续由 `.gitignore` 忽略，不把第三方源码提交进本仓库。
- `SOURCES.md` 记录仓库 URL、分支或标签、解析到的提交 SHA、拉取日期和版本 caveat。
- 1.20.1 精确参考优先使用 `mc1.20.1/dev` / `1.20.1`。
- 1.21.1 Create 源码参考跟踪 `mc1.21.1/dev` 的最新头部；构建依赖优先锁定已发布且可解析的最新稳定版本。目前远端最新稳定标签为 `mc1.21.1-6.0.10`，开发分支头部另行记录 SHA，避免把未发布 API 当成发布版契约。
- Create Phantom 只允许引用在线仓库 `https://github.com/yision1/CreatePhantom` 的代码，不建立或使用本地参考目录。
- 原有未分版本参考先整体保存在 `_legacy_pre_reorg_<timestamp>`，确认新参考可用前不删除。

- 重组 `ref/`，生成 `SOURCES.md`。

- 从 Create 1.21.1 的构建文件核对 NeoForge、Registrate、Flywheel、Ponder 与 MixinExtras 的准确版本和 Maven 坐标。

出口：

- 两个分支指向正确基线。
- `ref/SOURCES.md` 中的 SHA 可由本地检出复现。

## 阶段 1：构建、运行与发布基础设施

工作：

- Java 17 升级至 Java 21。
- LegacyForge 构建切换为 1.21.1 NeoForge ModDevGradle。
- 更新 Gradle Wrapper、仓库、依赖配置、资源展开和模组元数据。
- 将 `mods.toml` 迁移为 NeoForge 1.21.1 使用的元数据文件和依赖约束。
- 更新 Mixin 配置、refmap 生成和运行配置。
- 迁移 `test.py`、`quickPlayClient`、发布脚本及实例识别逻辑，使其识别 1.21.1 NeoForge 工件与日志。

出口：

- `processResources` 和最小 Java 编译任务可运行；源码错误形成可分类清单。

## 阶段 2：NeoForge 平台 API 与 Minecraft 1.21.1 API

工作：

- 将 `net.minecraftforge.*` 迁移到对应的 `net.neoforged.*` API。
- 迁移事件总线、生命周期事件、注册、配置、能力/附件、物品处理器和客户端事件。
- 迁移 1.21.1 的注册表、`ResourceLocation`、Holder、数据组件、物品堆 NBT、菜单和配方 API。
- 将旧 SimpleChannel 网络层迁移为 NeoForge payload 注册、编码和线程处理模型。
- 修复实体、方块实体、菜单、粒子、流体、战利品和数据生成接口变化。
- 保留原注册 ID；对旧 NBT 或组件数据增加必要的兼容读取。

出口：

- 主源码与悦灵物流源码通过 `compileJava`。
- 无残留的 Forge 包引用（明确兼容桥除外）。
- 网络包、配置和注册可在专用服务器类加载环境中安全加载。

- 按本地 Ponder 参考迁移 Ponder 插件、标签、场景和生成支持。

## 阶段 5：构建、Quick Play 与回归

验证顺序：

1. `clean compileJava`
2. `build`
3. 数据生成或资源校验任务
4. 专用服务器启动级检查
5. `quickPlayClient` 启动并进入测试世界
6. 检查 `latest.log`、Mixin 审计输出和崩溃报告

Quick Play 验收：

- 构建产物复制到正确的 1.21.1 NeoForge 实例。
- 客户端完成模组发现、注册、资源重载和世界加载。
- 玩家实体进入世界后出现可识别的成功标记，脚本正常退出并清理子进程。
- 日志不存在本模组引发的 ERROR/FATAL、失败注入或注册冻结异常。

功能抽样至少覆盖：

- 注册与创造模式物品栏
- 关键动力方块和方块实体
- 悦灵物流、菜单与网络同步
- 配方、JEI 展示和 Ponder 场景
- Flywheel/普通渲染回退
- 存档序列化与旧数据兼容读取

## 主要风险与处理顺序

1. **Create 开发分支与发布版漂移**：参考最新开发源码，但构建只锁定可解析发布版；出现差异时以发布依赖实际 API 为准。
2. **Mixin 静默失效**：逐个核对目标与生成 refmap，编译成功后仍必须运行客户端验证。
3. **网络层重写**：先建立统一 payload 注册骨架，再分批迁移包，避免双协议并存。
4. **数据组件替代物品 NBT**：保持旧数据读取路径，写入统一切换到新组件。
5. **客户端类加载越界**：将渲染、屏幕、JEI、Ponder 与 Flywheel 注册严格留在客户端入口。
6. **资源目录和 JSON 结构变化**：机械迁移后通过数据生成和启动日志逐项验证，不只依赖文件名检查。
7. **Quick Play 假阳性**：以实际进入世界和日志标记为准，不把“客户端进程启动”视为成功。
